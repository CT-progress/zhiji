# D13: 阶段 8 将控制面与数据面集成本地一体化应用

- **状态**: 计划中
- **日期**: 2026-10

## 背景

阶段 6 构建了完整的 Java 控制面（JWT 鉴权、Redis 限流、Resilience4j 熔断、RabbitMQ 编排、审计日志、Outbox 事件），阶段 7 完成了作品集交付（README、图示、ADR、演示脚本）。但两套系统至今并行空转——Web 前端仍然直连 Python FastAPI，Java 控制面独立运行在另一个端口上，两者没有端到端接通。

用户希望最终形态是一个可打包的本地一体化应用（桌面端前身）：Java 作为统一后端同时托管前端页面和 API，Python 退化为后台 worker，用户只感知一个入口。这是从"自托管工具"到"可打包产品"的关键一步。

## 决策

启动阶段 8，将 Java 控制面与 Python 数据面拼成统一入口的本地 Web 应用：

1. Java 托管前端静态文件 + API（统一入口，Spring Boot static 资源目录）
2. Python 退化为纯 worker（移除 Web 路由，只接收 dispatch + 回调）
3. 生产中间件切换（PostgreSQL + Redis + RabbitMQ）
4. 一键启动 + 打包（Docker Compose 多服务 + 非 Docker 本地方案验证）

阶段 8 之后，应用已是"一条命令启动的本地 Web 应用"，可直接作为桌面端前身——用 Tauri / Electron 包壳即可。

## 备选方案

1. 保持 Python 单体不变——简单，但无法利用 Java 控制面的鉴权 / 限流 / 编排 / 审计能力，且无法走向桌面端打包。
2. 用 Python 重写控制面能力——Spring Security / Resilience4j / Micrometer 在 Python 侧没有对等替代，重写阶段 6 成果是浪费。
3. Java 做纯 API 后端，前端独立部署——多一个进程和端口，不符合"一个入口"的桌面端前身定位。
4. Java 托管前端 + API 统一入口——已采纳，一个端口解决一切，天然适配桌面端。

## 推翻条件

集成后发现 Java 控制面的编排 / 限流开销大于收益（例如单机自托管场景下中间件运维成本超过安全保障收益），回退为 Python 单体。回退开关：`ZHIJI_DIRECT_PYTHON=1`。
