# D13: 阶段 8 将控制面与数据面端到端集成

- **状态**: 计划中
- **日期**: 2026-10

## 背景

阶段 6 构建了完整的 Java 控制面（JWT 鉴权、Redis 限流、Resilience4j 熔断、RabbitMQ 编排、审计日志、Outbox 事件），阶段 7 完成了作品集交付（README、图示、ADR、演示脚本）。但两套系统至今并行空转——Web 前端仍然直连 Python FastAPI，Java 控制面独立运行在另一个端口上，两者没有端到端接通。

这意味着 Java 控制面目前只是展示品：架构能力成立，但用户的实际请求不经过它。要让项目从"自托管工具"真正变成"可部署产品"，需要把控制面和数据面拼成一个统一系统。

## 决策

启动阶段 8，将 Java 控制面与 Python 数据面端到端集成：

1. 前端 API 请求从直连 Python 改为经过 Java 控制面（JWT 鉴权 + 限流 + RabbitMQ 编排）
2. Python 数据面退化为纯 worker（只接收 dispatch + 回调，移除 Web 业务路由）
3. 生产中间件切换（PostgreSQL + Redis + RabbitMQ 替换 H2 / SQLite / 内存）
4. 多服务编排部署 + 反向代理 HTTPS + 备份脚本

## 备选方案

1. 保持 Python 单体不变——简单，但无法利用 Java 控制面的鉴权 / 限流 / 编排 / 审计能力，项目停留在工具阶段。
2. 用 Python 重写控制面能力——用 slowapi 做限流、用 celery 做编排、自研 JWT——但 Spring Security / Resilience4j / Micrometer 在 Python 侧没有对等替代，且重写阶段 6 的成果是浪费。
3. 端到端集成——已采纳，将两套系统拼成一个产品。

## 推翻条件

集成后发现 Java 控制面的编排 / 限流开销大于收益（例如单机自托管场景下中间件运维成本超过安全保障收益），回退为 Python 单体。回退开关：`ZHIJI_DIRECT_PYTHON=1`。
